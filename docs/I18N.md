# Internationalisation

## Policy

1. The product default is **简体中文 (`zh_CN`)**.
2. On first start the OS locale is inspected (`LC_ALL`, `LC_MESSAGES`, `LANG`,
   then `locale.getlocale()`); QLocale is not used for the decision so that the
   rule is testable without Qt.
3. A Chinese locale of any region (`zh_TW`, `zh-HK`, `zh-Hans-CN`) resolves to
   `zh_CN`: Apeiron ships one Chinese translation, which serves those users
   better than English would.
4. Another supported locale resolves to that language (`en_*` → `en_US`).
5. An unsupported locale falls back to `zh_CN`.
6. A **manual** choice (`zh_CN` / `en_US`) is persisted and never overwritten by
   a later system-language change. Choosing “Follow system” restores detection.
7. The locale is **never** inferred from IP address or geographic region.

Implementation: `src/apeiron/i18n/languages.py` (pure functions) and
`src/apeiron/i18n/translator.py` (QTranslator lifecycle).

## Resource layout

```
src/apeiron/i18n/
  apeiron_zh_CN.ts   # generated by lupdate, filled by tools/build_translations.py
  apeiron_zh_CN.qm   # compiled by lrelease, shipped in the package
  apeiron_en_US.ts   # identity catalogue (source language)
  apeiron_en_US.qm
```

English is the source language of `qsTr()` strings. The identity catalogue keeps
the language switcher honest: selecting English reports `translated: true`
instead of “translation file missing”.

## Workflow

```bash
python tools/build_translations.py     # lupdate → fill → lrelease
python tools/build_translations.py --check
```

`--check` fails when a `qsTr()` string has no entry in the Chinese table, so an
untranslated string cannot reach a release build. `tools/build_translations.py`
holds the Chinese text keyed by the English source; editing the UI therefore
means adding one mapping entry.

The CI job `i18n` runs `--check` and verifies that both `.qm` files exist and
are non-empty.

## Missing or broken resources

`TranslationManager.apply()` returns a `TranslationState`:

| Situation | `translated` | `missing` | UI behaviour |
| --- | --- | --- | --- |
| `.qm` loaded | true | false | translated strings |
| `.qm` absent | false | true | source (English) strings, no crash |
| `.qm` corrupt | false | true | source strings, error logged |

Settings surfaces this state so a packaging mistake is visible instead of
silently mixing languages.

## Layout and fonts

- `QGuiApplication.setFont()` is given a candidate list that covers Simplified
  Chinese (`Noto Sans CJK SC`, `Source Han Sans SC`, `Microsoft YaHei UI`,
  `PingFang SC`, `WenQuanYi Micro Hei`) before Latin-only fallbacks, so CJK
  glyphs never degrade to tofu boxes.
- Chinese labels are shorter than their English counterparts in most cases;
  long English strings are wrapped or elided (`elide: Text.ElideRight`) rather
  than clipped.
- The navigation rail uses fixed 11 px labels with elision, and page headers use
  `wrapMode: Text.WordWrap`, so switching language does not reflow the layout
  into overlap.

## Adding a language

1. Add the code and display name to `LANGUAGES` in `languages.py`.
2. Add a translation table in `tools/build_translations.py`.
3. Run the build script; it writes `apeiron_<code>.ts/.qm`.
4. Add a resolution test (system locale → language, unsupported → fallback).
